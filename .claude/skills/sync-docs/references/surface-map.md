# Surface map

Exact detail for every downstream surface the `sync-docs` skill maintains. Each
entry lists the file, the sections that mirror `lib/documentation/`, and the
local conventions to match. Source of truth throughout is `lib/documentation/`
(`tags.ts` → `OPERATION_TAGS` is the master category list).

When in doubt about an example's output, look it up in
`engine/tests/expression/valid/*.txt`. The category ↔ test-file mapping is at the
bottom.

---

## README.md (repo root)

Audience: GitHub landing page, humans + agents evaluating the project.

Sync these sections:

- **Intro paragraph** (top) — the inline one-liner examples
  (`15 km to miles`, `derivative(2x^2, x)`, …). Keep representative of the
  headline categories.
- **"What is Hissab?"** — the prose sentence listing what you can write
  ("arithmetic, unit conversions, dates, statistics, probability, finance, IP
  subnet math, symbolic algebra, complex numbers, colors, bitwise…"). This is the
  category set in prose form; keep it consistent with `OPERATION_TAGS`.
- **Features table** — `| Category | Examples |`. **One row per `OPERATION_TAG`**,
  in the same order. When a tag is added to `tags.ts`, add a row here; the
  "Examples" cell should name real functions/operators from that chunk.
- **CLI section** — the `hissab …` command list must match `cli/README.md` and the
  actual CLI (`cli/src`). 
- **Engine Library section** — the exports paragraph (`Functions`, `Operators`,
  `Units`, symbolic token classes, `exprToLatex`) must match `engine/README.md`'s
  exports list and the engine's real root export (`engine/src/index.ts`).

Fences are ```text / ```ts and are **not** executed — verify their outputs by
hand against the test corpus or `pnpm -F cli dev eval`.

## app/src/docs/content/**/*.md  +  registry.ts

Audience: the in-app documentation UI. This is a **guide**, not a re-paste of the
chunks — it shows runnable examples and points at the source of truth for full
grammar (see the header comment in `registry.ts`).

Structure (mirrors `registry.ts` sections):

- `getting-started/` — onboarding pages (install, engine-library, cli,
  ai-calculations, skills, writing-expressions, faq). Not 1:1 with tags; update
  when install/usage/capabilities change.
- `guide/` — calculator categories: arithmetic, number-theory, percentages,
  finance, unit-conversion, compound-units, sets-combinatorics, logarithms,
  symbolic-algebra.
- `science-data/` — statistics, probability, trigonometry, date-time,
  number-systems, complex-numbers, bitwise, ip-addresses, colors.
- `workflow/` — labels-references, syntax-pitfalls.
- `reference/` — operators, functions, units (these mirror engine catalogs:
  `Operators`, `Functions`, `Units`).

Rules:

- **Every `OPERATION_TAG` has a corresponding guide/science-data page.** Add one
  when a category is added (e.g. `symbolic` → `guide/symbolic-algebra.md`,
  `complex_numbers` → `science-data/complex-numbers.md`).
- **Register every new page in `registry.ts`** under the right `DocSection`, with
  `slug`, `title`, and the `?raw` dynamic import. An unregistered page is
  invisible in the app.
- **Runnable examples go in ```hissab fenced blocks.** Every line in such a block
  must evaluate (the verifier enforces this). One expression per line; shared
  scope across the block (labels / `prev` / `line<N>` / `total<N>` resolve).
- **Wrong examples go in `:::caution` blocks** as prose bullets with inline
  `code` — never inside a ```hissab block.
- **Reference pages** (`reference/functions.md`, `operators.md`, `units.md`) are
  tables that mirror the engine's exported catalogs. When a function/operator/
  unit is added to the engine, add the row here.
- Keep outputs honest: pull results from `engine/tests/expression/valid/*.txt` or
  `pnpm -F cli dev eval "<expr>"`.
